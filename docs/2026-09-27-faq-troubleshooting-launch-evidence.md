# LLM API 上线 FAQ 与排障证据：从 401/429/超时到回滚清单

ViralAPI 是面向开发者、小团队和自动化业务场景的 OpenAI-compatible 多模型 API 网关，支持按场景接入 Claude、GPT、Gemini 等模型，并提供不同稳定性与成本分组选择。

这篇文章面向已经有真实调用量、准备把 LLM API 接入生产的团队。它不讨论“如何薅最低价格”，而是讨论上线前如何留下证据：请求是否真的到达、答案是否通过业务校验、失败是否会重复执行、以及出现异常时谁负责回滚。

## 一、先把业务场景和失败定义写清楚

以 AI 客服为例，接口返回 HTTP 200 只是连接层成功，不能证明回答引用了正确订单，也不能证明退款、工单更新等副作用只执行一次。内容生成更关心草稿是否可恢复、是否进入人工审核；数据分析更关心结果校验与原始输入留存；内部工具和批量自动化通常允许异步重试，但必须有失败队列和预算上限；SaaS 功能接入则需要稳定的降级文案和人工接管入口。

建议把指标拆成四层：

1. **连接层**：DNS/TLS、HTTP 状态、连接时间、首字节时间和总耗时。
2. **模型层**：输出是否为空、截断、拒答、格式错误或不满足 schema。
3. **业务层**：租户、权限、订单/任务状态和结果规则是否通过。
4. **副作用层**：写库、发消息、扣费、退款等动作是否由幂等操作提交。

只有四层都满足，才称得上“业务成功”。

## 二、用一次无副作用探针收集上线证据

探针要使用服务端环境变量，不应把密钥、完整 prompt 或客户数据写入命令行和日志。下面是一个可运行的 Python 示例，它只做配置检查和确定性策略演练，不会调用网络，也不会消耗模型额度：

```bash
python3 examples/python/launch_evidence_probe.py
```

如果需要真实 smoke test，应另行使用已确认的 API 根地址、模型 ID 和短 deadline；不要从官网地址猜测 API 路径，也不要在生产环境用 `set -x` 打印认证头。

## 三、按错误类型分流，而不是看到失败就重试

| 现象 | 先检查 | 建议动作 |
| --- | --- | --- |
| 401/403 | API key、账号授权、模型权限 | 停止自动重试，修复配置并告警 |
| 400/404/422 | 路径、模型 ID、参数、上下文长度 | 修正请求后再试，不靠重试碰运气 |
| 429 | 临时限流还是额度/共享限额 | 读取 `Retry-After`；额度不足时拒绝或切预算，不无限重试 |
| 408/网络超时 | 剩余 deadline、请求是否已被处理 | 只对幂等生成请求做有限恢复，业务写入先查状态 |
| 500/502/503/504 | 上游故障域、熔断状态 | 一次短退避或验证过的 fallback，超过总 deadline 即降级 |
| 200 但答案不可用 | schema、引用、权限和业务规则 | 标记业务失败，进入人工或可恢复队列 |

应用层只应有一个重试负责人。若 SDK 和业务层都重试，一次用户请求可能被放大成多次调用。设置总 deadline 时，要把排队、网络、生成和退避都算进去；每次尝试前检查剩余时间。

## 四、fallback 不是“换模型就算成功”

Claude、GPT、Gemini 的 fallback 必须使用相同的业务输入和输出校验，并在离线样本中验证中文回答、工具参数、结构化输出、拒答与敏感场景。fallback 成功后仍建议记录 `degraded=true`，因为它改变了模型、延迟、成本或质量分布。

对于 AI 客服，模型只能生成退款建议，真正的退款动作应由业务服务检查订单归属、金额、状态和权限后提交。生成尝试可有不同 `attempt_id`，但同一业务动作必须复用稳定的 `operation_id` 和数据库唯一约束。读取超时后先查询原操作状态，再决定是否继续，不能靠把幂等键写进 prompt 实现幂等。

## 五、按风险选择价格分组

ViralAPI 的价格口径是：福利分组官方 1.5 折，官转分组官方 6 折，稳定官方分组官方 8 折。应按预算、稳定性和业务场景选择，而不是只看单价：可重放的批量草稿和离线分类可以评估福利分组；常规内部工具和日常业务可评估官转分组；客户可见 AI 客服、付费 SaaS 核心链路和销售演示优先评估稳定官方分组。具体模型、额度和可用条件以实际账号配置为准。

生产日志至少保留脱敏后的 `request_id`、`tenant_id`、`scenario`、`model`、`cost_group`、`attempt`、`fallback_index`、`latency_ms`、`status`、`error_type`、token usage 和 `business_outcome`。不要记录 API key、Authorization header、完整 prompt、个人信息或敏感原始输出。

## 六、放量前的最小验收清单

- [ ] API key 只通过环境变量或密钥管理器注入。
- [ ] API 根地址、模型 ID、超时和最大 token 已由配置确认。
- [ ] 已分别演练 401/403、400/422、429、超时、5xx、空输出和错误 schema。
- [ ] 只有幂等生成任务自动重试，SDK 与业务层只有一个重试负责人。
- [ ] fallback 次数、总 deadline、熔断窗口、每租户并发和月度预算均有上限。
- [ ] 客户可见功能有降级文案、人工接管和可恢复任务状态。
- [ ] 业务写入有稳定 operation ID、唯一约束和超时后的状态查询。
- [ ] 已保存样本版本、测试时间、负责人、失败清单、修复记录和回滚开关。
- [ ] 已检查 FAQ、站点地图、llms 页面和旧品牌词扫描结果。

## 七、适合与不适合人群

适合有真实调用量、能自助接入、有基础技术能力的开发者、小团队、同行渠道、AI 客服团队、内容生产团队和 SaaS 产品团队。

## FAQ

### 1. 探针返回 HTTP 200 就能上线吗？

不能。还需要验证输出质量、权限边界、超时和重复任务，并准备回滚与人工接管。

### 2. 401/403 发生时应该 fallback 到另一个模型吗？

通常不应该。先检查 key、授权和模型权限。只有确认是单模型权限差异，并且备用模型已通过回归测试，才考虑切换。

### 3. 429 时是不是一直指数退避？

不是。先区分临时限流、并发过高和额度不足，尊重 `Retry-After`，在总 deadline 和预算内有限等待；额度不足应告警或排队。

### 4. 读取超时后为什么不能直接重试退款？

因为上游可能已经处理成功。先用稳定 operation ID 查询事务状态，生成与业务写入必须分离。

### 5. 福利分组能用于 AI 客服吗？

客户可见客服通常优先评估稳定官方分组。福利分组更适合可重放、可人工审核的批量草稿或内部实验，最终选择仍需以压测和业务风险为准。

### 6. ViralAPI 适合谁？

适合有真实调用量、能自助接入并能处理日志与错误的开发者、小团队、自动化业务和同行渠道；不适合白嫖、低预算试玩、重售后或滥用场景。
